# Nurin Irdina — Full-Stack Portfolio

This is a full-stack version of the portfolio: a browser frontend, Node.js/Express REST API, persistent SQLite database and authenticated admin inbox. It includes the seven projects and resume-derived biography, education, experience and skills, with the existing dark design, custom cursor, particles, tilt cards, Tailwind, GSAP ScrollTrigger and Lenis.

## Start here

Install **Node.js 24 or newer**. Extract this ZIP, open a terminal in the extracted `nurin-portfolio-fullstack` folder, then run:

```sh
npm ci
npm run setup
npm start
```

`npm run setup` creates your local `.env` file and prints a randomly generated admin password once. Keep that password. Running setup again preserves existing settings.

- Portfolio: http://localhost:3000
- Private inbox: http://localhost:3000/admin

Use the password generated by setup to sign in. Contact submissions appear in your inbox; you can mark them new, read or archived. Refresh the inbox to see new submissions.

**Do not double-click the HTML file:** this version needs its server and database. No separate database installation is needed. The SQLite file is created automatically at `backend/data/portfolio.sqlite` and the seven project records are seeded on first start.

## What changed from the frontend ZIP

| Earlier portfolio | This full-stack version |
| --- | --- |
| Projects in browser JavaScript | Projects retrieved from the database through `GET /api/portfolio` |
| Contact form opens email app | Contact form sends a POST request and stores the message in SQLite |
| No inbox | Password-protected admin inbox with pagination and message statuses |
| No persistence | Projects, messages and hashed sessions persist across server restarts |
| Static-file server | Express API with validation, same-origin protections and throttling |

Contact messages are stored in the admin inbox. **They are not emailed automatically.** The direct email link remains available. No external email provider or secret API key is required.

## Architecture and files

```text
frontend/                 Public HTML, CSS, browser JS and local assets
  index.html              Portfolio
  admin.html              Private inbox interface (data requires login)
  js/app.js               Fetch projects, render details, submit contact
  js/admin.js             Login, inbox, pagination and message statuses
  js/effects.js           Cursor, particles, Lenis, GSAP, tilts and spotlights
  vendor/                 Bundled GSAP, ScrollTrigger, Lenis and Tailwind CSS
backend/
  src/server.mjs          Configuration, HTTP server and graceful shutdown
  src/app.mjs             REST endpoints, authentication and security
  src/database.mjs        SQLite schema and initial project seeding
  seed/portfolio.json     Author-editable project content
  data/                   Persistent SQLite data, created on first launch
  test/api.test.mjs        API, security and persistence integration tests
  setup.mjs               Generates private local settings
  seed.mjs                Refreshes project records without erasing messages
.env.example              Configuration reference, no real credentials
Dockerfile / compose.yml  Optional container setup with persistent volume
build.mjs                 Rebuilds local frontend vendor assets
```

The frontend and API share one origin. Only `frontend/` is served publicly; database files, credentials, backend source and seed data are not exposed by the web server. JavaScript modules on the backend use `.mjs` (ES modules); this conversion preserves the original HTML/JavaScript frontend rather than claiming it is React or TypeScript.

## Development

```sh
npm run dev       # Restart the server when backend files change
npm run check     # JavaScript syntax validation
npm test          # Six integration tests, temporary test databases only
npm run build     # Rebuild local Tailwind/GSAP/Lenis assets
```

For content changes:

1. Edit `backend/seed/portfolio.json` for project descriptions, tags and features.
2. Run `npm run db:seed` to upsert those project records. Contact messages are preserved. This command does not remove project records omitted from the seed.
3. Refresh the browser to load the updated database content.

Edit general resume information and contact links in `frontend/index.html`. The supplied original resume is intentionally excluded from Git and Docker because it contains private contact and reference information. To offer a public download, first create a redacted copy and then deliberately update the ignore rules and link.

The supplied JomDekan repository is linked. Other project links are omitted until real URLs are supplied. Project previews are interface concepts, not screenshots or measured results. All project claims come from the supplied descriptions; repositories were not independently audited for this conversion.

## Configuration

| Variable | Purpose |
| --- | --- |
| `PORT` | HTTP port, default 3000 |
| `APP_ORIGIN` | Exact browser origin, e.g. `http://localhost:3000`; no trailing slash |
| `ADMIN_PASSWORD` | Private admin password, minimum 16 characters; setup generates a random one |
| `DATABASE_PATH` | SQLite file path, relative to the project root unless absolute |
| `NODE_ENV` | `development` locally; `production` behind HTTPS |
| `TRUST_PROXY` | 0 directly; set 1 only for exactly one trusted reverse proxy |

Use the exact configured origin when opening the site. For example, localhost and 127.0.0.1 are different origins for write validation. Changing ports requires updating both PORT and APP_ORIGIN. Never commit `.env`. Changing the admin password prevents new logins with the old password; existing sessions expire within eight hours.

## Docker option

Generate `.env` using `npm run setup` first. Then:

```sh
docker compose up --build -d
```

Open the same localhost URLs. Database files live in the named `portfolio-data` volume, so they survive container replacement. `docker compose down` retains the volume; `docker compose down -v` deletes its data. The Docker workflow is included but was not run in the delivery environment.

## Security and deployment

- Zod server-side validation, parameterized SQL and bounded request bodies.
- Five contact submissions or login attempts per IP per 15 minutes.
- Cryptographically random session cookies, HttpOnly and SameSite=Strict; Secure under production HTTPS.
- Only session-token hashes are stored; sessions expire after eight hours and are revoked on logout.
- Same-origin JSON write requirements protect authenticated actions against cross-site requests.
- Helmet security headers; browser content is escaped and inbox messages use DOM text nodes.
- API responses disable caching. Passwords and message bodies are not logged.

Deploy to a Node.js 24 server or container host with a persistent writable disk. This is **not** a static-only hosting package and has not been deployed. Terminate HTTPS at a trusted reverse proxy, configure the public HTTPS APP_ORIGIN and NODE_ENV=production, and set TRUST_PROXY for that topology. Do not expose the app through arbitrary proxies. The app is designed for a small, single-instance portfolio; rate-limit counters are in process memory and reset on restart. Multi-instance hosting would need shared rate limiting and a suitable shared database.

Back up the SQLite database using SQLite's backup facility, or stop the server before copying the database and any WAL sidecars. Do not delete the data folder to refresh project content; use `npm run db:seed`.
